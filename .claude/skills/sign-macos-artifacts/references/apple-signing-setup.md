## 1. Account prerequisites

| Requirement | Why |
|---|---|
| Membership is active and not expired | A lapsed membership invalidates signing and notarization |
| The person acting holds **Account Holder** or **Admin** | Only these roles can create Developer ID certificates and App Store Connect API keys |
| Latest Developer Program license agreement accepted | Creation is blocked until it is signed |
| Two-factor authentication on the Apple ID | Required for the portal and for key creation |

Confirm these first. If the acting account is a Developer or lower role, every
step below will fail at the portal, not in CI.

## 2. Developer ID Application certificate

Two routes; the Xcode route is simpler and needs no CSR handling.

**Xcode route (preferred).** Xcode → Settings → Accounts → select the company
team → Manage Certificates → `+` → **Developer ID Application**. Xcode creates
the certificate and installs it with its private key in the login keychain.

**Portal route.** Keychain Access → Certificate Assistant → Request a
Certificate From a Certificate Authority (saved to disk, no email) →
developer.apple.com → Certificates → `+` → **Developer ID Application** →
upload the CSR → download the `.cer` → import it so it pairs with the private
key generated by the CSR.

Gate:

```text
security find-identity -v -p codesigning
    # → one "Developer ID Application: PARTNERNET SOFTWARE PTY LTD (L2N7M5M544)"
codesign -dv --verbose=2 <signed-copy> 2>&1 | grep -E 'TeamIdentifier|Authority'
    # → TeamIdentifier=L2N7M5M544 and Developer ID Certification Authority
```

Then export for automation: Keychain Access → export the certificate **with its
private key** as `.p12`, protected by a strong password. The `.p12` and that
password are the two values automation needs; they are also the company's most
sensitive signing secret, unlike the Windows line where the key is
non-exportable inside Azure.

If the deliverable will be a `.pkg` or `.dmg` that needs stapling, also create
a **Developer ID Installer** certificate — see §6 before deciding.

## 3. Notarization credential

`notarytool` needs an App Store Connect API key, not a password. Create it at
App Store Connect → Users and Access → Integrations → App Store Connect API →
`+`, role **Developer**, and record three things:

- **Issuer ID**
- **Key ID**
- the `.p8` private key — **downloadable exactly once**; if it is lost, revoke
  the key and create another.

Store the `.p8` in the company vault at once. Gate, using a copy in a private
temporary location that is not the repository:

```text
xcrun notarytool store-credentials "<PROFILE_NAME>" \
  --key "<PRIVATE_P8_PATH>" --key-id "<KEY_ID>" --issuer "<ISSUER_ID>"
```

An Apple ID with an app-specific password also works interactively, but it is
tied to a person, breaks on 2FA changes, and has no place in CI. Use the API
key.

## 4. CI wiring (to be built when the credential exists)

Shape only; exact commands land with the implementation.

```text
# GitHub Environment: release-signing, macOS runner
secrets:  MACOS_CERT_P12_BASE64   MACOS_CERT_P12_PASSWORD
          ASC_API_KEY_P8_BASE64   ASC_API_KEY_ID   ASC_API_ISSUER_ID
variables: MACOS_SIGN_IDENTITY    # Developer ID Application: PARTNERNET SOFTWARE PTY LTD (L2N7M5M544)
```

1. Create a **temporary** keychain, import the `.p12`, unlock it, and set the
   keychain search list so only that keychain is consulted; tear it down in a
   trap so it exists only for the job.
2. `lipo` the x86_64 and arm64 slices into one universal binary **before**
   signing — the signature covers the fat file, so a later `lipo` invalidates
   it.
3. `codesign --sign "$MACOS_SIGN_IDENTITY" --timestamp --options runtime
   [--entitlements …] <binary>`, then `codesign --verify --strict --verbose=2`.
   Hardened runtime is what Gatekeeper expects.
4. Package for submission (`zip` for a bare binary, `pkgbuild`/`hdiutil` for
   those formats), `xcrun notarytool submit <payload> --keychain-profile
   "<PROFILE_NAME>" --wait`, then read the log JSON on failure.
5. `xcrun stapler staple <payload>` where stapling is supported — see §6.
6. Verify the final bytes: `spctl -a -t exec -vv <binary>` must be `accepted`,
   and the after-SHA must be recorded.

Every signature and every notarization submission is a provider transaction.
Record the submission id; keep provider logs in private company storage, never
in the public repository.

## 5. Repository policy and receipts

`release-policy.json` and `CODE_SIGNING_POLICY.md` currently define only
Windows: `signing.mode` governs `minicon.com` and the two native Windows
executables. macOS needs its own independent switch, its own fail-closed
behaviour, and its own receipt fields:

- before/after SHA-256 of the exact signed file;
- `TeamIdentifier` and certificate common name;
- notarization submission id and status;
- whether the payload was stapled, and the packaging format;
- `spctl` verdict from a macOS court.

A signature must never be inferred from a policy file, a certificate's
existence, or a test signing. It exists only when the shipped bytes verify.

## 6. Open design decisions (verify before implementing)

- **Packaging decides stapling — RESOLVED 2026-09-17 (measured on minicon
  v0.1.15).** A bare Mach-O **cannot** be stapled (`stapler` → Error 73), so the
  ticket never travels with the file: the signing receipt records
  `stapled=false` for the bare binary while the `.dmg` around it records
  `stapled=true`. Worse, Gatekeeper's GUI-launch path only trusts bundles —
  `spctl -a -t exec <bare-binary>` returns *"the code is valid but does not seem
  to be an app"* (rejected) **even when the binary is executed from inside a
  stapled, notarized `.dmg`**. The user-visible result is the "Apple could not
  verify this app is free of malware" dialog on double-click, although the
  binary is genuinely Developer ID signed AND notarized (Apple holds the ticket
  server-side).

  **Therefore a double-clickable macOS product must ship a `.app` bundle**
  (bundles are staplable and pass `spctl -t exec`). No Developer ID *Installer*
  certificate is needed for that — `.app` inside a `.dmg` or zip is enough. A
  CLI-only deliverable may stay a bare binary, but its first-run friction must
  then be documented: right-click → Open, or System Settings → Privacy &
  Security → Open Anyway, or `xattr -d com.apple.quarantine <path>`.

  Minimal bundle: `<Name>.app/Contents/MacOS/<exe>` plus `Contents/Info.plist`
  with `CFBundleExecutable` (= the exe file name), `CFBundleIdentifier`,
  `CFBundleName`, `CFBundlePackageType=APPL`,
  `CFBundleShortVersionString`/`CFBundleVersion`, `LSMinimumSystemVersion` and
  `NSHighResolutionCapable`. Sign inner-out (the executable, then the bundle)
  with `--options runtime --timestamp`; `ditto -c -k --keepParent` into a zip for
  `notarytool submit --wait`; then `stapler staple` **the `.app`** (not the zip)
  and re-zip for distribution. Verify with `spctl -a -t exec -vv <app>` →
  `accepted / source=Notarized Developer ID`.

  Because a bundle puts the binary at `Contents/MacOS/<exe>` and **not** on
  `PATH`, a product that is also a CLI needs an `install-cli`-style subcommand
  that symlinks it into `/usr/local/bin` (the VS Code `code` model).

  **Implemented in minicon v0.1.16.** `macos-signing.yml` assembles the bundle,
  signs inner-out, notarizes, staples the `.app`, asserts `spctl -a -t exec` is
  `accepted / source=Notarized Developer ID`, then places it in the `.dmg`.
  Asset *names* were deliberately left unchanged — only the `.dmg`'s contents
  differ — so `candidate_bundle.py`, the release workflow and the release policy
  needed no edits at all. **Copy that pattern** whenever a packaging fix must
  not put release-chain logic at risk. The signing receipt gained a
  `macos-universal-app` entry (the identity check reads assets by key with
  `.get`, so adding one is safe), and `install-cli` / `uninstall-cli` refuse to
  replace or delete anything that is not a symlink they own.
- **The APE `minicon.com` may be unsignable on macOS.** It is a PE/ZipOS hybrid,
  not a Mach-O, and `codesign` signs Mach-O. It executes on Darwin today, but
  execution is not Gatekeeper acceptance. Resolve this before promising macOS
  coverage for that artifact; the native universal Mach-O is the safe target.
- **Rehearsal consumes nothing on Apple's side** (no per-signature quota as on
  Azure Artifact Signing), but a rehearsal keychain must be removed afterwards.

## 9. Browser automation notes (for the next agent)

The setup was driven headlessly against the account holder's already-logged-in
browser. What mattered:

- **App Store Connect and developer.apple.com are SPAs whose controls are not in
  the accessibility tree.** a11y reads/clicks see only browser chrome. Drive
  them through **CDP** (`--remote-debugging-port`), not a11y. If the browser was
  launched without the port, relaunch it with the port and restore each
  profile's session; localhost health checks need `--noproxy '*'` when a proxy
  env is set, or they false-negative.
- The CDP **WebSocket handshake is rejected (403)** if the client sends an
  `Origin` header; connect with the origin suppressed. Use CDP
  `Runtime.evaluate` to read/click, and `DOM.setFileInputFiles` (with the file
  input's `objectId`) to attach the CSR — a page cannot set `input.files` from
  JavaScript.
- **Downloads open a native "Save" panel and a per-site "allow multiple
  downloads" prompt.** These are native windows, not web content: watch for the
  save sheet and the permission popup and click through them, or the file (an
  `.p8` is a one-time download) is silently lost. The macOS keychain access
  prompt (`SecurityAgent`) is **not** automatable; sign from a dedicated
  temporary keychain whose password you set, with
  `security set-key-partition-list`, instead of the login keychain.
- Certificate route used: generate the CSR + private key locally with `openssl`,
  select *Developer ID Application* + the **G2 Sub-CA** intermediary in the
  portal, attach the CSR by CDP, download the `.cer`, then
  `openssl pkcs12 -export` the key + leaf + G2 intermediate into the `.p12`.

## 10. Verified recipe (proven end-to-end 2026-09-13; CI-verified via a standalone court)

Rehearsed locally on the real minicon universal binary; every step confirmed.

```sh
# universal binary (candidate.yml already does this)
lipo -create minicon-x86_64 minicon-arm64 -output minicon

# dedicated signing keychain (never the login keychain — its prompt is not
# automatable); import the .p12 and open it to codesign without a GUI prompt
security create-keychain -p "$KCPW" "$KC"
security set-keychain-settings -lut 21600 "$KC"
security unlock-keychain -p "$KCPW" "$KC"
security import cert.p12 -k "$KC" -P "$P12PW" -T /usr/bin/codesign -T /usr/bin/security
security set-key-partition-list -S apple-tool:,apple:,codesign: -s -k "$KCPW" "$KC"
security list-keychains -d user -s "$KC" <existing keychains>

# sign the binary: hardened runtime + secure timestamp, chain to Apple Root CA
codesign --force --options runtime --timestamp --keychain "$KC" \
  --sign "$MACOS_SIGN_IDENTITY" minicon
codesign --verify --strict --verbose=2 minicon      # → satisfies its Designated Requirement

# notarize the binary (submit a zip; a bare Mach-O cannot itself be stapled)
ditto -c -k --keepParent minicon minicon.zip
xcrun notarytool submit minicon.zip --keychain-profile "$PROFILE" --wait   # → status: Accepted

# ALSO ship a stapleable, offline-verifiable container: a signed+notarized+stapled .dmg
hdiutil create -volname MiniCon -srcfolder dmgroot -ov -format UDZO minicon.dmg
codesign --force --timestamp --keychain "$KC" --sign "$MACOS_SIGN_IDENTITY" minicon.dmg
xcrun notarytool submit minicon.dmg --keychain-profile "$PROFILE" --wait   # → Accepted
xcrun stapler staple minicon.dmg                                            # → worked
spctl -a -t open --context context:primary-signature -vv minicon.dmg        # → accepted, Notarized Developer ID
```

**Confirmed behaviours:**
- The binary notarizes (Accepted) but `stapler staple <bare binary>` fails
  (Error 73) and `spctl -a -t exec <bare binary>` reports *Unnotarized Developer
  ID* — spctl's static exec assessment of a loose CLI executable does not do the
  online ticket lookup. So the tar.gz ships a signed+notarized binary that
  Gatekeeper clears **online**, and the `.dmg` is the **stapled, offline-clean**
  form. Ship both.
- The `.dmg` needs no *Developer ID Installer* certificate (that is only for
  `.pkg`). The Developer ID **Application** certificate signs both the binary
  and the `.dmg`.
- CI must import the `.p12` into a temporary keychain with
  `set-key-partition-list` and tear it down in a trap; the login-keychain prompt
  (`SecurityAgent`) cannot be automated.
