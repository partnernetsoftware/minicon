# bx 设计说明

## 1. 目标

给 agent 一个**调用成本接近系统调用、表达力接近脚本语言、执行单元是二进制**的工具。

三条硬约束：

1. **启动必须是解释器的下限，而不是运行时框架的下限。** agent 一次任务可能调用几十次脚本，每次 100 ms 的启动税会直接吞掉上下文预算之外的时间预算。
2. **能力必须是显式的。** 没有隐式 I/O、没有隐式依赖安装、没有隐式全局状态；脚本能做的事 = 内建暴露的事。
3. **必须能被 agent 自己扩展。** 加能力的路径要短到一次编辑 + 一次编译，而不是“改框架、发版本、等依赖”。

非目标：通用应用运行时、包生态、并发/异步、浏览器兼容。

## 2. 选型

| 方案 | 启动 | 表达力 | 扩展成本 | 结论 |
|---|---|---|---|---|
| node 脚本 | ~140 ms | 完整 JS | 需要包管理与版本矩阵 | 启动税不可接受 |
| 内嵌 QuickJS | ~2 ms | 完整 JS | 需 C 工具链与绑定层，VM 本身庞大 | 引擎好，但“脚本单元”仍是源码 |
| shell / `cmd /C` | ~10 ms | 几乎为零 | 无 | 无数据结构、无错误语义 |
| **自建字节码 VM（bx）** | **< 2 ms** | 够写脚本 | 加内建 = 一个函数 + 一行表 | 选中 |

关键判断来自用户的一句话：*“基础能力像 QuickJS，但执行的是二进制”*。因此最终形态不是“再写一个 JS 引擎”，而是：

- **源码**（`.bxs`）是给人/LLM 写的、可审阅的文本；
- **执行单元**（`.bxb`）是二进制字节码，`bx run` 直接执行它；
- **原语**是原生进程（`exec` / `sh`），返回值是结构化对象而不是待解析的字符串。

三者叠起来，既保留了“脚本可读、可 diff、可生成”，又拿到了“执行二进制”的启动与分发优势。

## 3. 架构

```
   .bxs 源码
      │  lexer  →  tokens（带行号）
      │  parser →  AST（Pratt 优先级）
      │  compiler →  Chunk[] + 常量池 + 行号表
      ▼
   .bxb 容器  ──encode──►  文件 / .bxcache 缓存
      │  decode（校验魔数、操作码、行号表）
      ▼
   栈式 VM  ──►  内建（exec / fs / json / 数组 / 字符串 / 环境）
      │
      └──►  子进程（stdout/stderr 独立线程排空，超时 kill）
```

模块边界（`src/`）：

| 文件 | 职责 | 变更频率 |
|---|---|---|
| `lexer.rs` | 字符 → token，行号，注释与转义 | 低 |
| `ast.rs` / `parser.rs` | token → AST，优先级爬升，语句终止规则 | 中 |
| `chunk.rs` | 指令定义、编译器、容器编解码、反汇编 | 中 |
| `vm.rs` | 求值循环、调用帧、索引/算术/比较语义 | 低 |
| `builtins.rs` | 全部能力面（63 个内建）+ 进程执行 | **高（扩展点）** |
| `value.rs` / `json.rs` | 值模型、结构相等、JSON 编解码 | 低 |

## 4. 语用决策

**语句以换行或 `;` 结束，不做 ASI。** 这是有意的：JS 的自动分号插入是 LLM 生成代码时最常见的静默错误来源（`return` 换行、行首 `(` / `[`）。bx 的规则是“行尾即语句尾，二元运算符后可续行”，解析是确定性的，错误是显式的。

**顶层 `let` 是全局；被闭包引用的局部是 cell，闭包按引用共享。** 编译前先算一次「本函数声明 ∩ 嵌套函数里出现的标识符」，只有这个交集里的局部与参数才装箱成 cell（`Rc<RefCell<Value>>`），普通局部仍是槽位；写回因此对创建者可见，循环变量每轮新建 cell，循环里创建的闭包各自保留当轮值。帧模型仍是固定大小的槽数组，只是槽里放的是指针。每个闭包按创建点可见的名字捕获（更外层通过创建者的 upvalue 逐层转发），所以嵌套任意深度都可读写。代价：每次调用多几次分配，且闭包携带的 upvalue 数随可见变量增加。

**点号调用是方法糖。** `s.split(",")` 编译成 `GET_GLOBAL "split"; s; ","; CALL 2`。这让 LLM 的 JS 直觉直接可用，同时不需要在值模型里引入方法表/prototype。反直觉的边界是：对象里的函数字段不能用点号调用，要用 `o["f"]()`——文档中明确。

**所有输出确定性。** 对象键用 `BTreeMap`，排序稳定；`json()` 紧凑且键序固定。这让测试断言、缓存键、diff 都可依赖。

**错误信息只描述一次来源。** 每条 VM 错误格式为 `script(line) in fn(): message`；跨调用传播时如果内层已经带位置就不再叠加前缀——早期的双重 `<eval>(1): <eval>(1):` 是 CALL 处无条件再包一层造成的，现已作为回归用例覆盖。
**错误用值表达，而不是语法。** VM 的错误本来就是一次 Rust 栈展开，因此补 `try/catch` 需要在每一帧维护 handler 栈。`attempt(f)` 用一次内置调用达到同样的目的：失败变成 `{ok:false, error}`，脚本可以记录、重试、继续。语法留白，行为不打折。

**迭代是一套统一协议。** `ITER_PREP` 在循环入口把数组/字符串/对象归一化成数组，`for x in …` 因此只有一条实现路径；类型不对时给出明确错误，而不是静默索引一个映射表得到 `null`（这正是 v0.1 的实际缺陷）。键值形式 `for k, v in …` 走 `ITER_KEYS`：对象给键、数组与字符串给下标，值统一用 `src[k]` 取，跨类型只有一条语义。

## 5. 字节码格式（v1）

小端。所有字符串 = `u32` 长度 + UTF-8 字节。

```
0   magic        "BXB\x01"
4   want_result  u8      eval 模式下保留最后一个表达式值
5   chunk_count  u32
    每 chunk:
      name        str
      arity       u16
      max_slots   u16
      code_len    u32
      code        code_len 字节
      run_count   u32
      runs        每条 { line: u32, count: u32 }
      const_count u32
      consts      每项 { tag: u8, payload }
```

常量 tag：`0` null、`1` bool(+u8)、`2` i64、`3` f64(bits)、`4` str、`5` func(chunk u32 + name)。

行号表按“连续相同行”行程编码：30 000 行脚本的 `.bxb` 从 4.7× 源码降到 1.9×（1.43 MB / 758 KB）。

`decode` 会校验：魔数、chunk 数上界、行号表总长 == 代码长度、每条指令长度合法、操作码已知。**不校验跳转目标**——`.bxb` 视为可执行内容，只运行可信产物。

## 6. 指令集

无操作数指令 1 字节；带操作数指令 5 字节（1 + i32 小端）。跳转操作数是**绝对指令偏移**。

| # | 指令 | 栈效果 |
|---|---|---|
| 0 | `HALT` | 返回栈顶 |
| 1 | `CONST i` | push consts[i] |
| 2–4 | `NULL` `TRUE` `FALSE` | push |
| 5–6 | `POP` `DUP` | 弹 / 复制栈顶 |
| 7–8 | `GET_LOCAL i` `SET_LOCAL i` | 局部槽读写（SET 弹栈） |
| 9–10 | `GET_GLOBAL k` `SET_GLOBAL k` | 全局读写（SET 弹栈） |
| 11–15 | `ADD` `SUB` `MUL` `DIV` `MOD` | 弹 2 推 1 |
| 16–17 | `NEG` `NOT` | 弹 1 推 1 |
| 18–23 | `EQ` `NE` `LT` `LE` `GT` `GE` | 弹 2 推 1 |
| 24–26 | `JUMP` `JUMP_IF_FALSE` `JUMP_IF_TRUE` | 弹条件 |
| 27–28 | `JUMP_IF_FALSE_OR_POP` `JUMP_IF_TRUE_OR_POP` | 短路求值 |
| 29 | `CALL argc` | 弹 argc 个实参 + 被调者，推返回值 |
| 30 | `RET` | 返回栈顶 |
| 31–32 | `MAKE_ARRAY n` `MAKE_OBJECT n` | 收 n / 2n 项 |
| 33–34 | `INDEX_GET` `INDEX_SET` | `[obj, idx] → v`；`[obj, idx, v] →` |
| 35 | `LEN` | 字符串/数组/对象长度 |
| 36 | `DUP2` | 复制栈顶两项（复合赋值取旧值） |
| 37 | `INDEX_SET_KEEP` | 写入并保留值（赋值表达式有值） |
| 38 | `ITER_PREP` | 归一化可迭代对象：数组原样、字符串→字符数组、对象→键数组 |
| 39 | `GET_UPVALUE i` | 读取闭包捕获的第 i 个值 |
| 40 | `MAKE_CLOSURE n` | 弹 n 个捕获值 + 函数常量，生成闭包 |
| 41 | `ITER_KEYS` | 键值迭代：对象给键、数组/字符串给下标（`v` 统一取 `src[k]`） |
| 42 | `GET_CELL i` | 读取局部 cell 里的值 |
| 43 | `SET_CELL i` | 写入局部 cell |
| 44 | `WRAP_CELL` | 把栈顶值装箱成新 cell（声明、参数、循环绑定用） |
| 45 | `SET_UPVALUE i` | 写入闭包捕获的 cell |
| 46 | `GET_UPVALUE_RAW i` | 原样取出 upvalue（创建闭包时转发更深层捕获用） |

调用约定：`[callee, arg1..argN] → CALL N → [result]`。调用帧是 `Vec<Value>` 槽数组，`max_slots` 在编译期算好，运行期不增长。

## 7. 资源与安全

| 边界 | 值 | 实现 |
|---|---|---|
| 调用深度 | 220 | `vm.rs` 帧计数；解释器跑在 64 MB 栈线程上 |
| 执行步数 | `BX_MAX_STEPS`，默认 1e9 | 每条指令递减 |
| 子进程超时 | 默认 120 s，可配 | `try_wait` 轮询 + kill |
| 子进程输出 | 默认 8 MB，可配 | 边读边丢弃，避免管道死锁 |
| 能力面 | 仅内建 | 无 `eval`、无反射、无动态加载 |
| shell | 仅 `sh()` | `exec` 默认不经过 shell |

## 8. 性能与归因

| 场景 | bx | node | 归因 |
|---|---:|---:|---|
| 冷启动（node 侧 spawnSync 测量） | 16–18 ms | 137–148 ms | bx ≈ 进程创建地板；差值是 node 自身初始化 |
| `fib(24)` 端到端 | 134 ms | 155 ms | VM 比 JIT 慢约 4×，但启动差距更大 |
| 30k 行脚本：源码 vs 字节码 | 239 ms → 70 ms | — | 省掉 lex + parse + compile |

结论：**在这个使用场景里，瓶颈是启动与解析，不是算术吞吐。** 因此优化优先级是“二进制执行 + 小体积”，而不是“更快的求值器”。

## 9. 路线图

1. 语法补齐：闭包捕获（环境数组）、`try/catch`、三元、字符串插值、正则（可外挂）。
2. 管道组合子：`run(["git","log"]) | first_lines(20)`，让“二进制编排”成为一等语法。
3. 能力令牌：脚本声明所需能力（`fs:read`、`exec:git`），VM 按声明拒绝越权调用。
4. DSH 原生工具：把 `bx` 注册为工具而不是 shell 调用，省掉外层进程。
5. 自举：测试运行器已经用 bx 写成（`tests/suite.bxs`），下一步是脚本格式化与 lint。

## 10. 已知取舍

- **闭包共享可变、逐层转发**：每次调用为可见局部装箱，更外层名字由创建者转发，换取任意深度读写与每轮独立捕获；代价是闭包 upvalue 数量随可见变量增长。
- **单线程**：`exec` 的并发靠子进程；VM 内不引入异步，避免给 agent 制造“看似并行实则串行”的陷阱。
- **无模块导出**：`use` 是文本内联，函数进全局。够用，且 `.bxb` 单文件分发更简单。
- **缓存放脚本旁**（`.bxcache/`）而非用户目录：沙箱环境下用户目录常不可写，缓存写失败必须不致命。
