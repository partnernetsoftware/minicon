## What shipped (the fix)

- **Correct CJK / double-width text on legacy Windows consoles.** The pre-ConPTY
  console-agent path (build < 17763 / Server 2016 / 14393) used to identify a
  wide-character continuation cell only by `COMMON_LVB_TRAILING_BYTE`, which is
  unreliable on legacy consoles — producing a stray space / ASCII between CJK
  glyphs and column drift. The fix derives continuation from character width via
  `unicode_width` (`c.width().unwrap_or(1) > 1`), the same oracle the vt100
  parser uses. Extracted into a platform-independent, unit-tested
  `agenterm-platform/src/adapters/console_row_emit.rs` (14 tests).

## Lessons (release-env fragility; see the release-safety memory)

Three snags hit this release — none are flow bugs, all were operator/understanding
mistakes worth not repeating:

1. **Use the native ARM Windows court for the Defender scan; do not fight the
   emulated x86 one.** `win-x86_64-desktop` is QEMU-TCG pure emulation (registry
   marks it `planned` / "not ready in 600 s"); its guest agent times out under
   the court's large-file transfer + scan load. Defender scans files statically
   without executing them, so `utm-win-defender-scan.sh` honours
   `MINICON_DEFENDER_COURT=win-aarch64-desktop` (native, already `ready`, VM
   `minicon-win-arm-64`). Guest ready in 24 s (vs 114 s), passed first try.
2. **The workflow `--ref` must point at the candidate's SHA, not `main`.**
   `reputation.yml` / `release.yml` assert `GITHUB_SHA == source_sha`. If `main`
   has advanced past the candidate SHA (e.g. a docs commit), `--ref main` fails
   at "Resolve exact Candidate". Create a throwaway branch at the SHA
   (`git branch candidate-src-<v> <sha>`), dispatch with it, delete after.
3. **`qualification_base64` is the local `qualify` output, not the raw court
   receipt.** Run `reputation_court.py qualify --manifest … --defender
   <court-receipt> --output <qualification>` first (kind
   `minicon-reputation-qualification`), then base64 that. A raw court receipt
   (kind `minicon-defender-court`) fails with "wrong reputation qualification
   kind". Pre-check locally with `reputation_court.py verify`.

**Root cause of the whole delay:** running a Win7 repro VM and repeatedly
open/quitting UTM in the same session poisoned the release court's UTM
automation bridge. Do not run exploratory VMs in the release UTM instance during
a release.
