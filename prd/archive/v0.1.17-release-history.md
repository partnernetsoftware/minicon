pre-release), dual-signed as always. It makes the composer's Send deliver a real
Enter key press, gives cross-tab read/write a file endpoint, and takes the
startup diagnostic out of the downloads.

## What shipped

### Send (Ctrl+O) now delivers a real Enter

The composer wrote the bracketed paste and its committing CR as **one buffer**,
so the child received `ESC[200~…ESC[201~\r` in a **single `read()`** — measured
directly with a raw-mode probe that prints every read boundary. A TUI that
applies a paste asynchronously (ink/React, Bubble Tea and friends) then handles
the CR first, while its input box is still empty: it submits nothing, and the
pasted text is left sitting there. That is exactly why such programs appear to
"need a real Enter press", which is how the owner reported it.

Two findings worth keeping:

1. **Splitting into two `write_pty` calls was not enough** — the kernel still
   delivered both in one `read()`. Only a real gap separates them, so the Enter
   is held for `COMPOSER_ENTER_DELAY` (12 ms) and written from the event loop's
   existing timer path (no blocking, no new thread).
2. **The payload must not keep its own trailing CR.** Keeping it *and* adding an
   Enter would submit twice: harmless in a shell (one blank prompt), but an
   extra empty message in an agent TUI.

The commit is also encoded through the **shared key encoder**
(`terminal_input::key_event_to_bytes` with the terminal's `TerminalKeyMode`),
the same path a physical Enter and `send-keys Enter` take, rather than a
hardcoded `\r`. In a terminal there is no separate "key event" channel — a key
press *is* those bytes — so today that is byte-identical to `\r` (verified: a
probe receives `b'\r'` from all three paths). Routing it through the encoder is
what keeps it correct if a negotiated keyboard mode ever changes what Enter
means.

Verified end to end: the child now reads the paste and the Enter as two chunks.

### Cross-tab read and write take files

`send-text --file PATH`, `send-paste --file PATH` and
`capture-pane --output PATH` — the practical half of what mux's `envelope`/`@file`
and `capture` provide. A payload passed as an argv word cannot survive
multi-line content, quotes, backslashes or the argument-length limit, and a
large capture should not have to cross a pipe. Measured: a file containing
quotes, backslashes, `$HOME` and backticks arrives byte-for-byte, wrapped in
bracketed paste so the receiver treats it as one paste rather than executing it
line by line.

Both are **client-side**: the wire carries only text, never a path, so the GUI
never opens a caller's file (a unit test asserts the path is absent after a wire
round trip). No server, queue or envelope format is introduced — the product
boundary (`no server, mux, MCP`) is preserved.

### The startup diagnostic left the downloads

`probe-imports.ps1` was copied into **every** platform archive, including Linux
and macOS where a PowerShell script is unusable — the owner noticed it in a
download and asked what it was, which is the whole argument against bundling it.
It is now published as its own Release asset, renamed
**`diagnose-startup-windows.ps1`** so the name states its purpose. The
old-Windows page previously told users to run `scripts/probe-imports.ps1`, a
path the archive never contained; it now says to download the asset and place it
beside `minicon.exe`.

## Open follow-ups (0.1.18)

- **Mouse does not work in Windows TUIs.** Confirmed working on macOS by the
  owner and by probe (`send-mouse` → child receives `ESC[<0;11;6M/m`), so the
  routing, encoding and mode detection are sound. The suspicion is ConPTY, which
  can break it in either direction: the child's `ESC[?1000h/?1006h` never
  reaching MiniCon (so it never forwards), or MiniCon's SGR reports never
  reaching the child. A Windows probe is prepared to tell those apart.
- `capture-pane --scrollback N` (needs cross-screen stitching and a decided
  semantics).
- A `[Quit MiniCon]` button on the greeting page: with no tabs, `CloseRequested`
  is swallowed by the empty-workspace early return in `ConApp::event`, so the
  window cannot be closed at all and the only way out is killing the process.
