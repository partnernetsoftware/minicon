## What shipped

### Pasting non-ASCII text works again on macOS

Reported by the owner: every paste containing a non-ASCII character failed with
`clipboard read failed: invalid utf-8 sequence of 1 byte from index 2`, in both
the terminal area and the composer. He could not even paste notes into a chat,
which is how severe this was in practice.

`pbpaste` encodes its output in the user's default text encoding, which is
derived from the locale environment. An app launched from Finder inherits almost
no environment, so on a machine whose system language is not English the helper
emits that language's legacy encoding. Measured on this Chinese macOS with the
clipboard holding `It's 中文`:

| environment | bytes |
| --- | --- |
| from a shell (`LANG` set) | `49 74 e2 80 99 73 20 e4 b8 ad e6 96 87` (UTF-8) |
| `env -i` (what a `.app` gets) | `49 74 a1 af 73 20 d6 d0 ce c4` (GBK) |

The GBK form stops being valid UTF-8 at index 2 — exactly the reported error.
The helpers now pin `LC_ALL`/`LANG` to a UTF-8 locale instead of inheriting
whatever the launcher provided (agenterm `28577d3d`).

Verified end to end under `env -i`: `Ctrl+Shift+V` then `capture-pane` returns
`It's 中文 🎉`. Negative control: with the pin removed, nothing arrives at all.

**Why it survived this long:** launching from a terminal masks it completely.
Every developer test ran from a shell; only a Finder launch on a non-English
system reproduces it. Worth remembering as a class — a `.app` runs in a
near-empty environment, and anything that reads the environment behaves
differently there.

### The Windows mouse works without configuration

0.1.18 shipped the classic console path as `{"console_agent": true}` in
`minicon.json`. The owner confirmed on his own Windows machine that grok CLI
answers the mouse on it. The path that works is now the **default**; ConPTY is
selected with `--feature conpty`, and the JSON key is gone (existing config
files keep parsing — unknown keys are skipped — so the key simply goes inert).

`--feature NAME[,NAME...]` is new: repeatable, comma-separated, `no-NAME` states
the off position, and an unknown name is rejected with the known set rather than
silently ignored. The split it encodes: `minicon.json` holds preferences a
person sets once and wants remembered; a feature selects which implementation
hosts the shell, which belongs to the invocation and should be visible in the
command line that reproduces a bug report.

### The ConPTY mouse question, settled — and two earlier answers withdrawn

This is the third answer this question has had. The first two were wrong, and
the reason they were wrong matters more than either of them.

**The instrument was unreliable and nobody checked.** Commands were being sent
to the Windows court through the QEMU guest agent, which runs them in **session
0** — not a session any user has, and not one whose console semantics match a
desktop. The identical probe there returned a `MOUSE_EVENT_RECORD` on one run
and 20 `KEY_EVENT`s on the next. Every conclusion up to that point came from
single runs on that instrument, including a nine-row elimination table that read
like proof. `utm-court interactive-exec` now supports Windows (session 1), and
with it every measurement below repeats 3/3 or 4/4.

**What is actually true.** Windows has two ways a program can ask for the mouse,
and the host path decides which one is served:

| host path | program asks via `ENABLE_MOUSE_INPUT` | program asks via `ESC[?1000h` |
| --- | --- | --- |
| classic console (default) | ✅ receives mouse records | ❌ never forwarded |
| ConPTY (`--feature conpty`) | ❌ one keystroke per report character | ✅ receives the SGR report |

Both halves are structural, not gaps to be closed:

- Under ConPTY, a program that asks the Windows way and also enables VT input
  gets the report passed through as text — upstream's open
  microsoft/terminal#15083. Windows Terminal inherits it.
- On the classic path, a program asks the terminal way by **writing
  `ESC[?1000h` to its own console**, which conhost consumes as a mode change.
  Those bytes never reach the host, so it cannot know to forward, and
  `send-mouse` correctly answers `route: selection`. A mode-aware injector was
  written to close this half and abandoned when the branch proved unreachable
  for exactly that reason.

**So the default is right for the reported case and the switch is the product
answer, not a workaround.** grok CLI asks the Windows way — confirmed on the
owner's own machine: it answers the mouse on the default path and not under
`--feature conpty`.

**Withdrawn:** the claim in this file's earlier revision that ConPTY "converts
an incoming report into a console record but never re-serializes it to VT bytes,
so a byte-reading TUI is blind" — measured false, 3/3: a byte-reading child
receives `ESC[<0;11;6M` intact through MiniCon's own ConPTY path. Also withdrawn
is 0.1.18's "ConPTY discards mouse input in both directions".

## Open follow-ups

- Whether a current `OpenConsole.exe` (which Windows Terminal ships, while
  third-party terminals get the older inbox `conhost.exe`) changes the ConPTY
  half. If it does, shipping that sidecar would make one path serve both kinds
  of program; if it does not, the split above is permanent.
- Wayland as a feature with X11 remaining the default — note that today there is
  no Wayland backend at all (the Linux path is `x11rb` only), so this is new
  capability, not a split.
- Headless / attach-detach GUI, wanted both for memory when detached and as the
  basis for a future mobile client attaching to a desktop session.
- `send-mouse --ctrl/--shift/--alt` modifiers; `capture-pane --scrollback N`;
  a black-box test pinning Send's two-read behaviour; `main.rs` split.
