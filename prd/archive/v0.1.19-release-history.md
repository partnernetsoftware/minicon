## What shipped

### Pasting non-ASCII text works again on macOS

Reported by the owner: every paste containing a non-ASCII character failed with
`clipboard read failed: invalid utf-8 sequence of 1 byte from index 2`, in both
the terminal area and the composer. He could not even paste notes into a chat,
which is how severe this was in practice.

`pbpaste` encodes its output in the user's default text encoding, which is
derived from the locale environment. An app launched from Finder inherits almost
no environment, so on a machine whose system language is not English the helper
emits that language's legacy encoding. Measured on this Chinese macOS with the
clipboard holding `It's 中文`:

| environment | bytes |
| --- | --- |
| from a shell (`LANG` set) | `49 74 e2 80 99 73 20 e4 b8 ad e6 96 87` (UTF-8) |
| `env -i` (what a `.app` gets) | `49 74 a1 af 73 20 d6 d0 ce c4` (GBK) |

The GBK form stops being valid UTF-8 at index 2 — exactly the reported error.
The helpers now pin `LC_ALL`/`LANG` to a UTF-8 locale instead of inheriting
whatever the launcher provided (agenterm `28577d3d`).

Verified end to end under `env -i`: `Ctrl+Shift+V` then `capture-pane` returns
`It's 中文 🎉`. Negative control: with the pin removed, nothing arrives at all.

**Why it survived this long:** launching from a terminal masks it completely.
Every developer test ran from a shell; only a Finder launch on a non-English
system reproduces it. Worth remembering as a class — a `.app` runs in a
near-empty environment, and anything that reads the environment behaves
differently there.

### The Windows mouse works without configuration

0.1.18 shipped the classic console path as `{"console_agent": true}` in
`minicon.json`. The owner confirmed on his own Windows machine that grok CLI
answers the mouse on it. The path that works is now the **default**; ConPTY is
selected with `--feature conpty`, and the JSON key is gone (existing config
files keep parsing — unknown keys are skipped — so the key simply goes inert).

`--feature NAME[,NAME...]` is new: repeatable, comma-separated, `no-NAME` states
the off position, and an unknown name is rejected with the known set rather than
silently ignored. The split it encodes: `minicon.json` holds preferences a
person sets once and wants remembered; a feature selects which implementation
hosts the shell, which belongs to the invocation and should be visible in the
command line that reproduces a bug report.

### The ConPTY mouse question, settled with bytes

0.1.18's notes claimed ConPTY "discards mouse input in both directions" and that
upstream had not implemented it. **That was wrong**, and the correction is
recorded in `v0.1.18-release-history.md`. Measured on the Windows-on-ARM court
with a standalone ConPTY host containing no product code:

| direction | ConPTY behaviour |
| --- | --- |
| child writes `ESC[?1000h` / `?1006h` | **relayed** to the hosting terminal |
| terminal's SGR report → `ReadConsoleInput` client | **converted** to `MOUSE_EVENT_RECORD` and delivered |
| terminal's SGR report → **byte-reading** client | **never re-serialized to VT** |

The control that pins it: send `A`, the SGR report, then `B` in one run — the
byte reader receives `41` and `42` and nothing between. So the channel works and
only the mouse fails to come back as bytes.

Three earlier probe runs "confirmed" the opposite and were all void: the probe
child inherited the redirected parent's std handles (`ftin=PIPE, ftout=DISK`)
and never spoke to the pseudoconsole, while still reporting a console window
handle. A ConPTY probe must open `CONIN$`/`CONOUT$` and assert
`FILE_TYPE_CHAR`. Probe and method are preserved in the `diagnose-terminal-io`
skill.

**Open, and deliberately not claimed either way:** Windows Terminal ships its
own `OpenConsole.exe`, while a third-party terminal calling
`kernel32!CreatePseudoConsole` gets the inbox `conhost.exe`, which lags. The
measurement above is of the inbox conhost on that court. Whether a current
OpenConsole re-serializes mouse to byte readers is untested; if it does, an
`OpenConsole.exe` + `conpty.dll` sidecar would make ConPTY viable — at the cost
of shipping Microsoft binaries alongside a product whose Windows executable is
660 KB. Do not assert "ConPTY cannot carry the mouse" without qualifying which
conhost.
