# v0.1.3 release history

Status: **archived after public v0.1.3 Promotion**. Current delivery truth is
`prd/PRD_02_27_con_delivery.md`; future `minicon.com` and signing work belongs
to v0.1.4.

## Decision record

The original v0.1.3 exploration tried to make `minicon.com` a fourth asset and
to couple trusted signing to Promotion. That plan was superseded after the APE
reputation and provider-signing work proved independent from native six-cell
coverage. The final ruling was:

```text
v0.1.3 = five unsigned native archives covering six OS/ISA cells
v0.1.4 = minicon.com + trusted signing through a policy switch
```

`release-policy.json` made the distinction fail-closed. Missing credentials do
not disable signing; only committed `signing.mode=off|required` selects the
court. v0.1.3 selected `off` and `assets.minicon_com=false`.

## Superseded rehearsals

- Run `33238478661` at `459d5cb` first proved one APE pack and six native
  status executions, but not GUI/control.
- Run `33244331387` at `5776086` added six GUI/control courts while payloads
  still identified as 0.1.2.
- Run `33250241396` sealed five platform archives plus `minicon.com`, but did
  not yet embed complete pack-host lifecycle evidence.
- Candidate `33250998985` carried an 8,909,564-byte APE that Defender detected
  as `Program:Win32/Contebrew.A!ml`; it was rejected and never promoted.
- Run `33259779184` proved the Authenticode-compatible APE header and empty
  signing slot. Ephemeral self-signing proved layout/tamper mechanics only; it
  never represented a trusted publisher.
- Run `33263135546` at `be2465f` produced a clean 7,517,987-byte unsigned APE,
  passed six GUI/control cells and a later exact-byte Defender diagnostic. It
  remained rehearsal evidence because the release ruling had changed.

These runs remain useful for v0.1.4 mechanism archaeology, but none is release
evidence for its eventual signed bytes.
