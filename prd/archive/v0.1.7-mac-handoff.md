# Handoff: publishing minicon 0.1.7 from a Mac mini

Audience: an agent or operator working on a **Mac mini**. Everything else is
context and can be skimmed. Follow the steps in order, keep the raw output of
every step, and stop to report when something does not match.

The release itself is four GitHub workflow dispatches. The only part that cannot
be done from a Windows or Linux host is the first one: producing the GHCR
six-grid bundle, because `scripts/six-cell-qualify.sh` cross-builds all six cells
from one Apple Silicon machine.

## Absolute constraints

Violating these damages the user's machine or the release record.

- **Never** bulk-kill minicon processes (`pkill minicon`, `killall minicon`,
  `Stop-Process`). A minicon under test shares a kill-on-close job object with
  the user's session; doing this has already killed the user's session once.
- Do not change test assertions or relax a gate to make CI green. If something
  fails, stop and report the original error.
- Do not add alignment gates (the alignment surface is saturated).
- Every failure: paste raw output. Do not summarise into a conclusion, and do
  not report a step that was not actually executed.

## Known state

- Repository: `partnernetsoftware/minicon`.
- `main == origin/main == 310963c` at handoff time. Working tree clean.
  Main has moved since this document was first written, so treat the revision
  above as the one to confirm in step 2 rather than as a literal to match: the
  release chain requires the `source_sha` you dispatch with to equal the
  `main` HEAD you actually built from.
- Version is already `0.1.7` in three places: `Cargo.toml`,
  `crates/minicon-core/Cargo.toml`, `release-policy.json`.
- `agenterm` is pinned to rev `7036c239`.
- `release-policy.json`: `signing.mode=off`, `reputation.mode=defender`.
- No `v0.1.7` tag exists yet.
- The release chain is `six-grid-runtime` → `candidate` → `reputation` →
  `release`.
- **Blocker**: `six-grid-runtime.yml` needs a GHCR bundle
  `ghcr.io/<OWNER>/minicon-six-grid@sha256:...`, which only
  `scripts/six-cell-qualify.sh` + `scripts/publish-six-grid-runtime.sh` produce.

`.github/workflows/six-grid-cloud-build.yml` is an abandoned experiment that
tried to build the cells on native CI runners. **Do not use it.** It proved the
native builds work but is not part of the release path.

## Steps

### 1. Environment self-check

Report anything missing. Do not guess and do not auto-install.

```sh
cd <minicon clone>
git status --porcelain          # must be empty
git rev-parse HEAD
command -v git cargo python3 gh jq oras shasum
cargo xwin --version
cargo zigbuild --version
gh auth status
```

### 2. Confirm the revision

```sh
git fetch origin && git checkout main && git pull --ff-only
git rev-parse HEAD              # record as <SHA>
```

### 3. Six-cell qualification

Expected 30–90 minutes. This cross-builds all six cells from this machine.

```sh
./scripts/six-cell-qualify.sh
```

Report:

- the per-cell PASS/FAIL summary,
- `source_tree_sha256`, `source_dirty` and `summary` from
  `target-six/receipt.json`,
- any FAIL cell and its log path.

Notes: the script refuses a dirty tree, and the receipt's `source_tree_sha256`
must equal the current `scripts/source-fingerprint.py` value.

### 4. Publish the bundle (only if step 3 fully passed)

This packages, pushes to GHCR, and dispatches `six-grid-runtime.yml` itself.

```sh
OWNER=$(gh repo view --json nameWithOwner -q .nameWithOwner | cut -d/ -f1)
./scripts/publish-six-grid-runtime.sh "ghcr.io/$OWNER/minicon-six-grid" test
```

Report every field the script prints, especially:

- `published=<ghcr.io/...@sha256:...>`
- `dispatched=<run URL for six-grid-runtime.yml>`

### 5. Wait for the runtime workflow

```sh
gh run list --workflow six-grid-runtime.yml --limit 3
```

Record its run id as **①**.

### 6. Dispatch `candidate`

Read `.github/workflows/candidate.yml` first and use its real input names.

```sh
gh workflow run candidate.yml -f source_sha=<SHA> -f upstream_run_id=<①>
```

Wait for green. Record the run id as **②**.

### 7. Reputation qualification (needs an active-Defender Windows guest)

`reputation.yml` does **not** take just a candidate run id. Read
`.github/workflows/reputation.yml` first: it requires `qualification_base64`,
the base64 of a redacted `reputation-qualification.json` produced by the
Defender court. GitHub's Windows runners disable Defender, so this cannot be
scored on CI.

On the Mac, with a UTM Windows guest that has Defender active:

```sh
# CANDIDATE_DIR is the unpacked candidate and defender-receipt.json is the court
# output; the court fails closed on a hit, missing engine metadata, or a
# different executable SHA.
./research/minicon-com-loader/utm-win-defender-court.sh <CANDIDATE_DIR> defender-receipt.json
python3 research/minicon-com-loader/reputation_court.py qualify \
  --manifest <CANDIDATE_DIR>/candidate-manifest.json \
  --defender defender-receipt.json \
  --output reputation-qualification.json
base64 < reputation-qualification.json | tr -d '\n' > qualification.b64
gh workflow run reputation.yml \
  -f candidate_run_id=<②> -f source_sha=<SHA> \
  -f qualification_base64="$(cat qualification.b64)"
```

Wait for green. Record the run id as **③**.

If Defender reports a false positive, submit the exact sealed `minicon.com` at
Microsoft's sample portal and rerun the same-SHA court after the classification
updates. Do not disable Defender, add exclusions, rebuild, or remove behaviour
to manufacture a green verdict.

### 8. Dispatch `release`

Read `.github/workflows/release.yml` first. `confirmation` is
`publish-v0.1.7` (or `dry-run-publish-v0.1.7` for a dry run).

```sh
gh workflow run release.yml \
  -f candidate_run_id=<②> -f source_sha=<SHA> \
  -f reputation_run_id=<③> -f version=0.1.7 -f confirmation=publish-v0.1.7
```

Wait for green. Record the release URL, the `v0.1.7` tag, and the asset list.

### 9. Backfill the release ledger

Edit `prd/archive/v0.1.7-release-history.md`: replace the `TBD` rows with the
real receipts (run ids, digest, tag, timestamps) and set

```
Status: **released <YYYY-MM-DD>**
```

Commit only that file and push.

## If something blocks

Report exactly what is missing (Apple SDK, `oras` login, missing rust target),
the commands you ran, and the raw error, then stop for the user to decide. Do
not work around a missing tool silently.

## Notes for the operator

- Steps 3, 4 and 7 are the only Mac-required parts: the cross-build needs an
  Apple Silicon host, and the Defender court needs a UTM Windows guest. The
  rest runs anywhere.
- The workflow input names above are written from memory. Confirm each against
  its workflow file rather than trusting this document.
- `scripts/lib/sha256-file.sh` prefers `sha256sum` and falls back to `shasum`,
  so it works on macOS without changes.
