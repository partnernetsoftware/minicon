# v0.2.11 release history — 2026-10-15

Hotfix release. v0.2.10 crashed shortly after a busy TUI (codex via
mycodex.bat) started: `0xc0000005` in GDI32.dll (offset 0x226c), twice in
the owner's Windows Application event log at 10:53 and 10:55 local.

## Root cause (0.2.10 regression)

`9892242` fixed the StretchDIBits sub-rect quirk by offsetting the DIB bit
pointer to the band origin — but the offset included the **column
component** (`source.top * stride + source.left`) while `biWidth` stayed
the full frame stride. GDI reads `biWidth` pixels per row from the offset
start, so the final row ran `source.left` u32s past the end of the
`width*height` pixel buffer. A bottom-band present (bottom == frame
height) with left > 0 — which a busy TUI emits constantly — read out of
bounds on every partial present; when the read crossed a page boundary
GDI32 faulted. v0.2.9 never executed this path (full-frame presents).

## Fix (commit c0214e8)

- `band_present_read_window()` — single derivation of the read window;
  the present offsets the pointer by whole rows only and asks for a
  full-stride band (biWidth = stride, biHeight = exposed rows). The paint
  DC clips output to the update region, so the extra columns cost clipped
  blits, not pixels. `offset + len` ends exactly at the buffer end for
  bottom bands, strictly inside for interior bands.
- New regression test
  `band_present_read_window_stays_inside_the_frame_buffer` pins the crash
  case (720x400, band 40..680 x 300..400) and proves the 0.2.10 form out
  of bounds. A `debug_assert` guards the contract at the call site.
- Test-suite gap the owner called out: 0.2.10 shipped green because
  nothing asserted the present read window against the buffer extent —
  the band math was inline at the call site. Closing that class of hole
  is why the derivation is now a tested pure function.

## Incidents

1. **Signing dispatched without `qualification_only`** — the input is
   required but gh accepted the omission; the workflow's `if
   [[ "$QUALIFICATION_ONLY" == true ]]` then took the qualification
   branch, receipts came back `release_eligible: false`, and the first
   Candidate (38692505370) correctly rejected them. Re-dispatched both
   signing courts with explicit `-f qualification_only=false`; receipts
   then `true`. Dispatcher error, recorded here. (The 0.2.10 chain hit
   the same class: qualification base64 passed as a file path.)
2. **Defender `Update-MpSignature: RPC failed`** twice (06:44, 06:48) —
   the known Microsoft service window fault (0.2.9 precedent). Third
   attempt green. No workflow changes, as the discipline requires.
3. **Local disk exhaustion (D: 0 bytes free)** blocked the alignment
   guard mid-chain (`no space on device`). Freed ~20G: agenterm/target
   12G (owner approved; the safe-delete hook initially blocked bulk
   deletion until confirmed), recycle bin cleared by owner. Note:
   rm -rf of two target trees ran 42 minutes deleting nothing because a
   live `minicon-winmgr` process (owner's taskbar, PID 274380) held
   winmgr/target; that tree was skipped, not killed.
