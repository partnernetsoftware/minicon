# v0.2.7 release history

Published 2026-10-13 under the owner's standing instruction to drive 0.2.7 to a
public release. Source: `f52662a`.
Public release: https://github.com/partnernetsoftware/minicon/releases/tag/v0.2.7

## Scope

Three things, in the order they were asked for, plus a fourth the third forced:

1. **Window-icon parity (GitHub: the icon report).** 0.2.6 registered its
   Windows window class with a null `hIcon`, so the caption and taskbar showed
   the generic system default rather than the executable's own icon, and X11
   had no window icon at all. Windows now loads its own PE icon group
   (`winresource` id 1) into the class and pins it with `WM_SETICON`; X11 is
   handed RGBA that `build.rs` decodes from the same committed
   `assets/minicon.ico`. One committed icon, no derived blob, no PNG decoder in
   the binary. macOS keeps the icon its `.app` already carries: the runtime
   path for the bare `.tar.gz` binary needs `objc2` as a direct platform
   dependency and is a named gap, not a claim.
2. **`Shift+Enter` sends**, alongside `Ctrl+O`. Bare `Enter` stays the soft
   newline. The chord is in the keymap table, so `--help`, the settings panel
   and both READMEs list it. This also restored the `--help`/README shortcut
   gate that 0.2.6 left broken (the sent-history panel's chord was listed in
   the settings panel and the README but never in `--help`).
3. **A manual check-for-updates flow** (GitHub issue #4). A new **Updates**
   section in the settings panel shows the running version and three controls
   whose availability is the phase: Check, Update, Restart. The GitHub
   `releases/latest` document is read through the existing bounded
   `network_http` client; the version comparison is `minicon-core`'s numeric
   one; the archive is verified against its published SHA-256 sidecar and the
   executable extracted by name with a small in-product reader for the two
   shapes the release ships. The swap is rename-aside then place-new with a
   rollback and a retained backup; the restart is a separate explicit press.
   macOS opens the release's own `.dmg` instead of swapping inside a signed
   bundle. Manual and per-press only — nothing runs at startup, on a timer or
   in the background.
4. **A TLS-provider fix to the outbound client**, forced by (3). `ureq` picks
   its TLS provider at runtime and defaults to Rustls, while the manifest
   enables exactly one per host; on Windows that mismatch made the first
   `https://` request — the update check — panic inside `ureq`. Confirmed by
   the new opt-in real-GitHub smoke, not by any default test, because every
   default test speaks `http://` to a loopback server. `network_http` now pins
   the provider to the feature the build enables. This is the one change in
   0.2.7 that no offline gate could have caught; see the chain notes below.

Explicitly **not** in 0.2.7, each recorded as a named gap rather than left
implied: code-signature verification of the downloaded binary (the in-tree
inspectors sit behind the `app-facts` feature), and the macOS runtime icon for
the bare CLI binary. The measured cost of the update feature is +152 KB on the
local `release` build (1,713,152 → 1,868,800 bytes).

## Post-release security review of the update path

An independent adversarial read of the new fetch → checksum → decode → swap
path, run after publication. It confirmed the verification order and every
network bound, and found **four defects in code that had already shipped**.
They cannot be fixed in 0.2.7 (a public Release is immutable), so each is filed
as a priority leaf in `plan/plan-v0.2.8.md` with a verified line number and a
proposed fix:

- `{EXECBIT}` — a Unix in-place update installs a non-executable binary (the
  staged file's mode is never set; the tar header's mode field is discarded).
- `{ROLLBACK}` — the failed-launch rollback re-enters `commit_swap`, which
  deletes the very `.backup` it needs; the destination ends up empty with the
  old binary gone. `{EXECBIT}` is what makes this reachable on Linux.
- `{BOMB}` — the archive decode has no output ceiling; a crafted or tampered
  release aborts the process by exhausting memory.
- `{SCHEME}` — `validate_url` admits `http://` and the asset URL is unpinned.

None of the four is reachable without the release document itself being hostile
(the document arrives over TLS from the GitHub API), which is why this is a
follow-up rather than a recall. Full detail, evidence design and priority are in
`plan/plan-v0.2.8.md`.

## Notes for the next chain

- The first `minicon-com` dispatch for this version (run `38365447953`, SHA
  `417f595`) failed in the macOS pack: the withdrawn macOS runtime-icon code
  used `NSImage::alloc`, whose `ClassType` trait is not in scope under the
  unix pixel-window feature set. No cell ran. The cause and the local gate that
  would have caught it are recorded in `plan/archive/plan-v0.2.7.md` and
  `prd/PRD_02_32_dev_loop_crosscheck.md` "Local per-host gates".
- The second dispatch (run `38368374768`, SHA `b3aca41`) passed all six cells —
  the macOS gate fix works — but was **superseded before signing**. While it
  ran, the opt-in real-GitHub smoke exposed a second defect (below), whose fix
  landed as `f52662a`, so the artifacts had to be repacked from that SHA. The
  six cells are cheap; shipping a broken updater is not. The chain above packs
  from `f52662a`.
- **The TLS provider defect.** `ureq` selects its TLS provider at runtime and
  defaults to Rustls, but the Windows manifest enables only `native-tls`, so
  the first `https://` request — the update check — panicked in `ureq`'s
  transport ("provider is Rustls but feature is not enabled: rustls").
  `crates/minicon-platform/src/network_http.rs` now pins the provider per host.
  This is invisible to every default test (they all speak `http://` to a
  loopback server), which is why the real-GitHub opt-in has to be run by hand
  before a release: see `plan/archive/plan-v0.2.7.md`, "A defect the offline gate cannot
  see".
- **The macOS signing attempt 1 failure was an Apple network flake, not a
  defect.** `notarytool submit` for the `.dmg` returned `Accepted`, then
  `xcrun stapler staple` on the same `.dmg` failed with
  `Error Domain=NSURLErrorDomain Code=-1005 "The network connection was lost"`
  talking to `api.apple-cloudkit.com/.../ticket-delivery` (exit 68). The
  binary's own notarize+staple had already succeeded in the same job. Rerunning
  the failed job (`gh run rerun 38370626761 --failed`) passed unchanged. A
  stapler/CloudKit outage is not something this product can fix or cause.
- `release.sh <version>` stops before its first dispatch when `Cargo.toml` and
  `release-policy.json` already read the version, so this chain was driven with
  the dispatches the skill encodes, with `source_sha` pinned to `main` HEAD.
  `workflow_dispatch` rejected the bare SHA as a `ref` (HTTP 422, "No ref found
  for"), so the pack was dispatched `--ref main` while `main` HEAD *was* the
  intended SHA; `minicon-com.yml` takes no inputs.
- **Every step from signing on was dispatched `--ref candidate-src-0.2.7`**, a
  throwaway branch pinned at `f52662a`, rather than `--ref main`. `release.sh`
  uses `main` for steps 2-5 and the branch only from step 6, which is correct
  only while `main` HEAD is exactly `source_sha` and nobody pushes during the
  chain. This repo had a concurrent session that could move `main`, and the
  product-source-hash drift check would then have failed every in-flight run.
  A branch pinned at the SHA is the same ref for the whole chain and is immune
  to that; it is deleted at the end either way. `GITHUB_SHA` and the
  checked-out `HEAD` both equal `source_sha` on it, so the identity assertions
  are satisfied identically.
