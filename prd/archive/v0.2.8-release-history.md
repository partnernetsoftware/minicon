# v0.2.8 release history

Published 2026-10-14 under the owner's standing instruction to fix every open
0.2.8 defect and then drive the release, with the version number left to the
driving session. Source: `dd5ddff2a390b9ab19c016c94333ae9ae9a081c9`.
Public release: https://github.com/partnernetsoftware/minicon/releases/tag/v0.2.8

## Scope

One outcome, chosen before any code was written: **an update never leaves the
user with a product that cannot start.** Everything else in the release is
either a user-reported defect or the delivery decision that outcome forced.

1. **The update path can no longer brick an install.** 0.2.7 shipped a Linux
   in-place update that installed a **non-executable** binary — staging set no
   file mode and the tar reader discarded the header's — so `spawn` failed
   `EACCES`, and the rollback that failure triggered re-entered `commit_swap`,
   which deleted the very `.backup` it needed. The install ended up holding a
   file that could not launch with the previous one already gone. Five leaves,
   landed in one change on `24e8435`:
   - `{EXECBIT}` — `apply_staged_mode` copies the destination's own mode onto
     the staged file before the rename (`cfg(unix)`, fallback `0o755`). The
     destination is runnable by definition, so this cannot install a
     non-runnable file.
   - `{ROLLBACK}` — `rollback_swap` is **one** rename and a separate verb from
     `commit_swap`, returning `Result` so it cannot be silently dropped. A
     rollback that itself fails is `FailureKind::LaunchUnrestored`, the one
     state allowed to say "you may need to reinstall".
   - `{BOMB}` — every archive reader takes a `decoded_limit` derived from the
     download bound, the inflate pre-allocation is checked against it **before**
     allocating, and going past it is the typed `ArchiveError::TooLarge`
     instead of a memory-exhaustion abort.
   - `{SCHEME}` — `require_secure_url` refuses anything but `https` before a
     request is constructed, with loopback as the single exemption the offline
     tests need.
   - `{RECOVER}` + `{SLOGAN}` — `Phase::Failed` now carries a typed `Failure`
     whose kind states whether the install is intact, restored or unknown, and
     `UiLanguage` renders it as a **localised** sentence naming the retained
     backup file and the next step (the raw token is published on
     `ui-snapshot` so automation does not parse prose). The README line and
     release notes now name that backup too. Also `clear_stale_staged` removes
     a `*.update` left by a session that staged and never swapped — the half of
     "nothing left behind" that was still untrue.
2. **A clipboard image pastes as a temp-file path on both paste surfaces**
   (`a8da22e`). The composer had an image fallback; the terminal content area
   did not, so `Ctrl+V` there answered `clipboard read failed: clipboard
   unsupported`. Both surfaces now share one decision in a new module so they
   cannot drift apart again. The image side re-encodes rather than dumping
   bytes: `CF_DIB` carries no `BITMAPFILEHEADER`, so the raw bytes are not a
   file any viewer opens, and a BMP of even one screen is far too large for the
   model that reads the path.
3. **The scrollbar scales against the scrollback that exists** (`2bb0ec5`).
   `vt100`'s `scrollback_len` is the *configured* capacity — thousands of rows
   on a session that has printed three — and `scrollback_bounds` fed it to the
   scrollbar as the maximum, so a fresh session drew a full-length bar over
   phantom rows. A new `scrollback_depth` reports the live `VecDeque` length
   instead.
4. **The `minicon.com` Candidate ceiling was raised 11 → 11.75 MiB**
   (`dd5ddff`), an explicit dated owner decision (2026-10-14). See "Artifact
   budget" in `prd/PRD_02_27_con_delivery.md`. This was forced by (1): the
   sealed `minicon.com` grew to 11,622,574 bytes, 88,238 over the stamped
   ceiling, and the 0.2.7 pack was already only 124,472 bytes under it.

Explicitly **not** in 0.2.8, each recorded as a named leaf rather than dropped:
`{SIGV}` (verify the signature, not only the sidecar — a PRD_02_27 size
decision), `{RESTART}`, `{PREF}`, `{HIST}`, `{FIND}`. All five move to 0.2.9;
`plan/plan-v0.2.8.md` "Deferred to 0.2.9" keeps each with its owner.

## Notes for the next chain

- **The macOS `stapler` / CloudKit flake recurred, exactly as 0.2.7 recorded
  it.** The first macos-signing dispatch (run `38511521457`) notarized both the
  `.app` and the `.dmg` to `Accepted`, stapled and validated the `.app`, then
  failed on `xcrun stapler staple` of the `.dmg` with
  `Error Domain=NSURLErrorDomain Code=-1005 "The network connection was lost"`
  talking to `api.apple-cloudkit.com/.../ticket-delivery` (exit 68). Apple's
  system-status page was all green, and the workflow's two `stapler staple`
  calls have **no retry**. This is the second known occurrence of the same
  Apple-side flake (v0.2.7 hit it at `macos-signing.yml:283` too). Handled the
  way the skill's troubleshooting reference prescribes for transient CI infra —
  a bounded re-dispatch, both attempts recorded — and a **fresh** dispatch
  (`38511823195`) passed. It was deliberately *not* fixed by editing the
  workflow: `macos-signing.yml`'s preflight asserts `GITHUB_SHA == source_sha`,
  and `GITHUB_SHA` is the dispatched ref's tip, so any commit moving `main`
  invalidates an in-flight `source_sha` and forces steps 2–3 to repack. If this
  flake keeps recurring, a bounded retry around the two `stapler staple` calls
  is the right standing fix — it does not weaken the gate, because `stapler
  validate` and `spctl` still follow.
- **The chain was driven by hand from step 2.** `release.sh 0.2.8` skipped its
  bump step (the version had already been bumped in `0f1d335`) and stopped
  before dispatching; steps 2–3 were run by a resume copy of `release.sh`
  (bump step replaced by `SHA=$(git rev-parse HEAD)`, everything else verbatim),
  and after the macOS re-dispatch steps 4–8 were resumed with a second copy
  that pins the three already-green upstream run ids. This is the documented
  hand-drive path (`scripts/release.sh` header; 0.2.5/0.2.6/0.2.7 all hit it).
- **A Windows-host hazard worth keeping:** the driver scripts were written
  through a Windows file-writing tool that defaulted to **CRLF**, so a
  `SHA="…"` assignment carried a trailing `\r` — which would have silently
  corrupted every `== source_sha` assertion with no error message. Verify any
  generated shell script with a byte check (`CR == 0`) before running it;
  `grep -c $'\r'` in Git Bash misreported 104 CRs on a file that had none.
- **Retracted claim (a follow-up review, 2026-10-14).** An earlier revision of
  this note said local `cargo clippy --all-targets` / `minicon_alignment` could
  not run because "the sandbox blacklists `reg.exe`". That was wrong and is
  withdrawn. Evidence to the contrary, gathered on the Windows host:
  `reg query "HKLM\SOFTWARE\Microsoft\Windows Kits\Installed Roots" /reg:32`
  returns normally (exit 0), the SDK's `rc.exe` exists at
  `…\Windows Kits\10\bin\10.0.22000.0\x64\rc.exe`, and both gates pass from a
  cold, separate target directory — `cargo test --test minicon_alignment`
  **15 passed** and `cargo clippy --all-targets -- -D warnings` clean. The real
  hazard is that **Windows will not let cargo delete a running executable**:
  `tests/minicon_alignment.rs` reads `option_env!("CARGO_BIN_EXE_minicon")`, so
  cargo builds the `minicon` bin for the test, and a MiniCon left running from
  this tree holds `target\debug\minicon.exe` (`failed to remove file … 拒绝访问
  (os error 5)`). Renaming a running image is allowed, deleting it is not, so a
  separate `CARGO_TARGET_DIR` is the fix. The Python self-tests for the two size
  scripts (`candidate_bundle.py --self-test`, `loader/write-size-report.py
  --self-test`) were run directly and pass at the new ceiling.
- A leftover **local** `candidate-src-0.2.7` branch (its remote was already
  deleted during the 0.2.7 release) was found and deleted alongside
  `candidate-src-0.2.8`; both `local` and `remote` are empty of
  `candidate-src-*` as of this release.
- One finding recorded but deliberately **not** planned: the user-reported
  "flashing". Diagnosis (2026-10-14 session, read-only) traced it to `vt100`
  marking the whole grid damaged on every scroll (`grid.rs` `scroll_up` /
  `scroll_down` call `mark_full` unconditionally), so ordinary output
  re-rasterises the entire window; the Windows and unix raster paths then
  amplify any partial change to a full-frame present. A root-cause fix needs a
  viewport-scroll damage primitive in the vendored parser — a contract change
  that wants its own spec and does not belong in a correctness release. The
  new clipboard-paste async polling was checked and **exonerated**.
