## Scope

One outcome, stated before any code was written (`plan/plan-v0.2.9.md`):
**a choice made in the settings panel is still in force at the next launch —
and it is kept in the same hand-editable `minicon.json` the product already
reads.** Everything else in the release hangs off that outcome or is recorded
as a named, deliberately-not-done leaf.

1. **`{PREF}` — the product's first *write* path to `minicon.json`.** Until
   this release the product only ever *read* three numeric keys; the file was
   the user's to edit and the panel's choices died with the process. Landed in
   `bd14eec`:
   - the hand-written codec (`crates/minicon-core/src/json.rs`) gains two
     string-valued keys (`theme`, `language`) and a checked number emitter
     (`JsonValue::decimal`), with the malformed/wrong-type cases tested;
   - `ConConfig` carries typed `theme`/`language`, `load_config` splits into a
     testable `config_from_bytes`, and the **stable id is persisted, not the
     display label** — `ThemeChoice::from_tag` and `UiLanguage::from_tag` are
     proven inverses of the ids the control surface already publishes;
   - `write_config_to` publishes through the existing
     `minicon-platform::filesystem_publish::write_file_atomic`, and the
     document is rebuilt from the in-memory mirror so `cols`/`rows` are carried
     over a rewrite rather than dropped; keys never set are omitted entirely;
   - safe failure is per-key for an unknown id, whole-file for a malformed
     document, and a write that cannot be published leaves the previous file
     alone and reports a host notice instead of panicking. A font press at
     either clamp writes nothing (`with_font_gesture` compares before/after).
2. **`{RESTART}` — a Restart states what it costs before it is pressed.**
   `UiLanguage::restart_cost(tabs)` renders the real tab count and that running
   children stop, in all three languages, and never invents "0 tabs"; the panel
   paints it exactly while a Restart is possible, and `ui-snapshot` publishes
   `update.restart_cost` unconditionally so automation can assert it without
   staging a release.
3. **`{HIST}` — the owner's own two follow-ups, both landed.** Every sent line
   carries the **destination label** it was sent to (read from the tab tree at
   send time, not the OSC title — an adjacent duplicate updates its
   destination rather than keeping the first), and the panel **scrolls past its
   capacity** by wheel, clamped at both ends, with paint, hit-test and
   `ui-snapshot` all reading the one `history_visible_offset` clamp.

Explicitly **not** in 0.2.9, each a named leaf rather than dropped:

- **`{SCROLL-DAMAGE}` — spec written, code deliberately not touched.** The
  reported "flashing" is real and its root cause is verified
  (`third_party/vt100/src/grid.rs` `scroll_up`/`scroll_down` call `mark_full()`
  unconditionally, so any output at the bottom of a full screen invalidates the
  whole client). But its spec — `plan/plan-scroll-damage.md`, written first as
  the leaf's own dependency required — found the leaf **cannot deliver its
  outcome as scoped**: the vendored crate is a `[patch.crates-io]` path, not a
  workspace member, so its exact-visible-cell damage oracle is not executed by
  any gate; and both shipped hosts upgrade every frame to full
  (`src/main.rs` transient-host and Windows-`con` paths), which the leaf's
  non-goal excludes. The parser narrowing is a prerequisite, not the fix. Two
  questions are recorded for the owner in `plan/plan-v0.2.9.md` open decision 5:
  which leaf owns the two host amplifiers, and whether the fork joins the
  workspace or gains a gate script. `prd/PRD_02_24_con_terminal.md`'s damage
  ledger now carries a `[-]` row stating that the neighbouring `[v]` claim
  ("ordinary output requests only the affected rows") is wider than the code.
- **The engineering consolidation track** (`{SPLIT}`/`{SEAM}`/`{ENCAP}`/
  `{FEAT}`/`{NAME}`/`{DOC-OWNER}`) — carried in `plan/plan-v0.2.9.md` with
  evidence and an order, deliberately never gating the product track, and not
  started. `{FEAT}` and `{DOC-OWNER}` still need owner decisions before any
  removal.
- `{FIND}` (blocked on C1 scrollback semantics) and `{SIGV}` (blocked on the
  `prd/PRD_02_27_con_delivery.md` size decision), unchanged from the plan.

## Notes for the next chain

- **The Defender court hit a ~35-minute Microsoft-side signature-update
  outage, and the recovery path is now proven.** All four first attempts of
  `defender-ci-scan.yml` run `38542540642` (2026-10-14 09:27–09:56 UTC) died
  at the `Update-MpSignature` step with `The remote procedure call failed` —
  four *fresh* runner VMs of the same `win25-vs2026/20260925.250` image that
  had scanned the 0.2.8 Candidate green at 04:36 UTC the same morning
  (run `38512296363`). Not our bytes: real-time protection is off on hosted
  runner images (the explicit scan runs *after* the failing step), the
  extraction step succeeded identically every time, and the same error class
  has cross-project precedents (microsoft/netperf 2026-01,
  kubernetes-sigs/image-builder 2021, actions/runner-images discussion #161).
  Attempt 5 (10:01 UTC, after a 15-minute backoff) went green end to end with
  no change to bytes or assertions — a bounded retry with backoff, never a
  skipped scan, per the skill's troubleshooting reference. Both the failures
  and the successful attempt are recorded here.
- **`defender-ci-scan.yml` now pins `runs-on: windows-2022` (commit `7f14757`)
  — but that fix could NOT take effect for this Candidate, and the reason is a
  trap the 0.2.8 notes had already spelled out for `macos-signing.yml`.**
  The scan's Bind step asserts raw `GITHUB_SHA == source_sha` *in addition to*
  the product-source-hash comparison; a fresh dispatch must run `--ref main`
  while `main`'s HEAD *is* the source SHA. Pushing the image-switch commit
  moved `main` past `e7b36a7`, so the fresh dispatch died at
  `GITHUB_SHA does not match source_sha`, and a rerun of the original run
  re-executes the workflow file *frozen at* `e7b36a7` — i.e. still
  `windows-2025`. The product-hash tolerance in the Bind protects
  pinned-branch gates (reputation/release) and rerun contexts; it does **not**
  keep the fresh-dispatch path open once `main` moves. 0.2.9's scan therefore
  completed on `windows-2025` (the fleet recovered), and the `windows-2022`
  pin benefits the **next** chain. Lesson repeated from 0.2.8 and recorded
  again with its exact mechanism: **during a chain, push nothing to `main` —
  not even an infra-only fix you have half-verified.**
- The `windows-2025` host labels in `prd/PRD_02_27_con_delivery.md`'s
  defender-court rows were updated to point at the workflow file as the
  authority for the host, with the 2026-10-14 image switch noted, so the PRD
  and the workflow cannot drift apart silently again.
- As in 0.2.8, the chain was hand-driven from step 5: `release.sh 0.2.9` ran
  the bump and steps 2–4, its background process was reclaimed by the agent
  sandbox mid-chain, and steps 5–8 were resumed with dispatches matching the
  skill's manual path exactly (`run-reputation-and-release` §"The four
  gates"), with every `-f` input name verified against the workflow files and
  `release-policy.json` read before the publish (the pre-flight the earlier
  hand-drives had skipped). The throwaway `candidate-src-0.2.9` branch was
  deleted after the Promotion and no stale `candidate-src-*` branches remain.
